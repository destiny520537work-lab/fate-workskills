# 对抗审稿

把材料当作一个严格审稿人会看到的版本来检查。目标不是找语气问题，而是提前发现会让核心结论失效的证据漏洞。

## 原则

- 结论必须能追溯到代码行、原始数据、实验记录或一手材料。
- 事实、推断和未验证假设分开标记。
- 找错与保留有效结论同样重要，不因为发现局部问题就否定全部工作。
- 若审查对象由当前会话生成，尽量使用隔离上下文进行独立复核。运行环境支持且用户允许时，可让独立 reviewer 只读取待审材料和证据路径；不要提供辩护性背景。

## 九项检查

每一项都要给出“无此问题 / 部分成立 / 成立”及证据位置。

1. **循环论证**：结论是否用某个定义出来的指标重新证明该定义本身？
2. **提示泄题**：所谓“发现”是否已经作为答案写入 prompt、规则或标签？
3. **实现与宣称不符**：逐个核对“并行”“全量”“不可篡改”“实时”等关键动词。
4. **混杂变量**：一次实验是否同时改变多个因素，却把结果归因给其中一个？
5. **样本量与措辞不匹配**：小样本或单次案例是否被写成普遍规律？
6. **开发/测试污染**：测试集、held-out 条件或评测标准是否参与过选择和调参？
7. **威胁模型边界**：安全或鲁棒性结论在哪些攻击者能力和系统假设下成立？
8. **数字可复算**：成本、指标、归一化和聚合结果能否从原始记录独立重算？
9. **证据分级**：当前材料更适合内部报告、探索性 pilot、预印本还是正式投稿？到下一档还缺什么？

## 产出格式

1. **置顶严重问题**：必须修的实现错误或证据断裂，用 🔴 标记。
2. **逐条判定表**：问题｜判定｜证据位置｜影响｜修复办法。
3. **措辞降级清单**：原宣称 → 证据真正支持的说法。
4. **仍然成立的结论**：明确保留经复核后站得住的部分。
5. **证据等级与最小补齐清单**：说明提高可信度所需的最小实验或材料。

## 质量门槛

- 关键判断是否指向了可检查的位置，而不是只写“可能有问题”？
- 是否区分了实现 bug、实验局限和措辞过度？
- 是否检查了反例、替代解释和缺失对照？
- 是否避免编造不存在的代码、数字或评审标准？
- 是否明确写出尚未读取或无法验证的部分？
